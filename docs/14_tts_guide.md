# 14 · 语音合成 / TTS

**本项目内没有任何语音模型代码。** 合成全部交给独立的 **TTS service**
（`Agent_TTS_Module`），这边只剩一个地址、一层薄客户端、和一次朗读友好化的 LLM 调用。

先前的两个本地后端（`qwen3_ov` / `qwen3_torch`）已经**删除**。原因不是「服务更时髦」：
同一件事维护两份实现，两边的音质、参数、失败处理迟早对不上，而 TTS 模块已经把
权重轮动、失控生成拦截、音色克隆/设计、字幕这些都做完并实测过了。

---

## 1 · 分工

```
DailyNewsAssistant                     Agent_TTS_Module（一个进程，一份权重）
────────────────────────────────       ──────────────────────────────────────────
tts/preprocess  朗读友好化（1 次 LLM） →  :8300/tts/synthesize   单段合成
tts/segment     清洗 + 按句分段        →  （服务内还会再按模型上限分块）
tts/service     逐段发请求 + 拼接波形     权重加载 / 8GB 轮动 / 失控重试
tts/subtitle    字幕（SRT）               音色克隆 / 音色设计
tts/supervisor  探活 + 自动拉起        →  :8300/gui              （TTS 自带界面，DNA 不再用）
tts/client      HTTP（httpx）          →  :8300/tts/synthesize   三种 mode 都走这一个
```

**只有一个进程、一个端口。** 界面挂在服务的 `/gui` 上，与服务**共用同一个模型**。
先前是两个独立应用（8300 服务 + 8301 界面），实测**各加载一份权重**：1.7B 就是
两份几 GB，8 GB 卡上直接顶满，而且点一次外部界面要等第二个进程冷启动。
The GUI is mounted on the service: one process, one copy of the weights.

依赖也跟着变干净了：`pip install -e ".[tts]"` 现在只装 `httpx` ——
没有 torch、没有 openvino、没有 transformers，连 numpy 都不需要（拼接用标准库 `wave`）。

## 2 · 配置（`.env`）

| 变量 | 默认 | 说明 |
|---|---|---|
| `TTS_SERVICE_URL` | `http://127.0.0.1:8300` | 服务地址。**换机器只改这一行** |
| `TTS_GUI_PATH` | `/gui` | 图形界面在**同一个服务**上的路径 |
| `TTS_GUI_URL` | 空 | 只有界面单独部署时才填（填了就不再拼接） |
| `TTS_MODULE_DIR` | 空 | `Agent_TTS_Module` 根目录，**只为自动拉起** |
| `TTS_PYTHON` | 空 | 拉起用的解释器，空 = 当前这个 |
| `TTS_AUTOSTART` | `true` | 关掉就只报「不在线」，不代为启动 |
| `TTS_START_ATTEMPTS` / `TTS_START_TIMEOUT` | `3` / `120` | 拉起次数与单次等待上限 |
| `TTS_REQUEST_TIMEOUT` | `900` | 单段合成的 HTTP 超时 |
| `TTS_PREPROCESS` | `true` | 朗读友好化开关（唯一的 LLM 调用） |
| `TTS_ARTIFACT_DIRNAME` | `tts` | 逐段音频与附件放在文章目录的哪个子目录 |
| `TTS_SUBTITLES` | `true` | 默认合成路径是否顺带导出 SRT |
| `TTS_MODE` | `voice_clone` | 默认怎么发声：克隆 / 内置音色 |
| `TTS_REF_AUDIO` | `ref_audio/qwen3-tts-cpu.wav` | 参考音频，相对路径按**数据目录**解析 |
| `TTS_REF_TEXT` | 空 | 参考音频的原话；**空 = 纯 x-vector 克隆** |
| `TTS_REF_AUDIO_GUEST` / `_TEXT_GUEST` | 空 | 嘉宾的参考音频；空 = 嘉宾用内置音色 |
| `TTS_VOICE_HOST` / `TTS_VOICE_GUEST` | 空 | 内置音色，空 = `Serena` / `Uncle_Fu` |

> 引擎 ABI 与操作台交互上踩过的坑，根因见
> [issues/012](issues/012-tts-engine-abi-and-console.md)。
>
> `TTS_REQUEST_TIMEOUT` 别往小改。CPU 上实测 RTF≈13，一段 120 字要三四分钟，
> 默认的 20 秒超时会在**服务正常工作时**把请求掐掉 —— 那是最难查的一类失败。

## 3 · 探活与自动拉起

```
用之前 → GET /health（3 秒超时）
         在线 → 直接用
         不在线 → 能自动拉起吗？
                   不能（关了 / 远程地址 / 没配 TTS_MODULE_DIR）→ 报错并说清是哪一条
                   能 → python -m agentic_tts.cli serve，等就绪，最多 3 次
                        3 次都失败 → 上报「TTS 不可用」，附上手动排查命令
```

三次而不是无限重试：第一次可能只是**冷启动慢**（加载权重几十秒），第二次能排除
偶发的端口竞争，第三次还不行就不是运气问题，而是环境不对，继续重试只是把一个
确定的失败拖长。

两条实现上的取舍：

- **子进程日志写到 `data/logs/tts_service.log`**，不丢弃 ——
  拉起失败时唯一能说明原因的东西就在那里（缺依赖、端口被占、权重路径错）。
- **Windows 上子进程脱离控制台组**（`CREATE_NEW_PROCESS_GROUP`）：
  否则工作台被 Ctrl+C 时，这个共用的服务会跟着一起死。
- 退出时**不杀**服务：它是共用的，CLI 与别的项目可能还在用。

## 3.5 · 默认发声方式：音色克隆

**默认克隆 `data/ref_audio/qwen3-tts-cpu.wav`，不是内置音色。**

为什么不用内置音色作默认：内置音色**跟着权重变**。同一个名字（`Serena`）在
0.6B 与 1.7B 上并不是同一把嗓子 —— 服务端换个 checkpoint，这边的声音就变了，
而且没有任何报错。克隆锁的是一个音频文件：文件不换，声音就不换。

| | 主持人 / 旁白 | 嘉宾 |
|---|---|---|
| 默认 | 克隆 `TTS_REF_AUDIO` | **内置音色 `Uncle_Fu`** |
| 配了 `TTS_REF_AUDIO_GUEST` | 同上 | 克隆那一份 |

嘉宾默认不跟着克隆同一个文件：访谈稿两个人一把嗓子，听众分不出谁在说话，
双角色就白做了。

`TTS_REF_TEXT` 留空 ⇒ 走**纯 x-vector 克隆**（只取音色，不需要原话）。
填了才走 ICL 克隆，而上游硬要求它与音频一字不差 —— 不知道原话时编一句会让
克隆质量明显变差，所以默认留空。

两条不会静默降级的地方：

- **参考音频不存在** → 记一条 WARNING 并回落到内置音色。这条警告的意思是
  「声音和你预期的不是同一把嗓子」，值得当真。
- **克隆模式下不再往服务端传音色名**：服务端把「既有 `ref_audio` 又有音色名」
  当成互相冲突的参数直接报错（它故意不做静默忽略）。

远程服务（4060 那台）会自动把参考音频**转成 base64** 送过去：路径是在服务端
解析的，这边的 `C:/…/ref_audio/x.wav` 在那边不存在，而报出来的错会是
「参考音频不存在」—— 看起来像文件丢了，其实是机器不对。

## 4 · 默认路径（单段合成）

工作台点「合成音频」，或 `dna produce <id> --kind narration_audio`：

1. 读稿子（长文案读 `.json` 附件里的角色轮次，其余解析 Markdown 的「口播」段）
2. **朗读友好化**：一次 LLM 调用（见 §6）
3. **分段**：只在句子边界切，每段 ≤120 字
4. 逐段 `POST /tts/synthesize`（`encoding=base64`，一次一段）
5. 本地拼接：段间 0.25s 静音，**换角色 0.5s**
6. 写 `narration_audio.wav`，记台账
7. 写字幕 `narration_audio.srt`（**和音频同名同目录**，`TTS_SUBTITLES=false` 可关）
8. 把**逐段音频**写进 `<文章目录>/tts/`（`seg_001_host.wav` …）

> **一篇文章一个文件夹，重做就覆盖。** 不按次数或时间戳再分一层：分层之后
> 「这篇的音频到底是哪一份」要靠人比时间戳，而人只会打开最上面那个。
> 服务端那边同理 —— 产物目录名按「文章+产物+语言」固定，重做覆盖同一个目录。

> 逐段文件写的是**合成时已经拿到的字节**，不回头去服务端下载。服务端按
> 「段号 + 音色」命名，一次合成里同一个音色出现两次就会互相覆盖（实测踩到），
> 下载回来的是错的那一份。

**为什么一段一个请求，而不是把整批丢给 `/tts/batch`**：
整批一个请求下去，界面在几十分钟里只能看一个转圈，而且中间失败一段就整批失败。
逐段发才能报「第 7/23 段」，也才能一段失败只丢那一段。服务端本来就是串行合成
（一把锁，8GB 卡上并发必然 OOM），逐段发不会更慢。

一段失败**不会**毁掉整条：`failed_segments` 记下来，界面上明说「音频不完整」——
重跑要几十分钟，把能用的先留住，但绝不能让人把残缺音频当成品发出去。

## 5 · TTS 操作台（主界面内建）

展开面板里音频那一格的 **「TTS 操作台」** 按钮（`frontends/nicegui_app/tts_panel.py`）。
点它**不会开始合成** —— 这是第 4 项实测反馈的根因：从前那里是一个紧贴「合成音频」
的开关，瞄着开关点常常命中按钮。

界面见 [13_workbench_guide.md](13_workbench_guide.md#tts-操作台) 的示意图。
这里只记实现上的硬约束。

面板的工作顺序是 **整篇 → 分段 → 逐段 → 拼接**：

```
顶部「整篇文案」框（打开时＝稿子正文，可整篇改）
  → [按此文案拆分]（`console.resplit(text, max_chars=框里那个数)`）
  → 分段列表（每段可改字、单独配音色、▶ 生成、🎲 换种子）
  → [全部生成]  逐段跑 ○ 与 ✎，✔ 跳过
  → 全部 ✔ 之后底栏按钮变成「拼接并保存（无需重新合成）」
     —— `rendered` 覆盖了每一段，后端一段都不会重发
```

**字幕按这次的分段出**：`build_cues` 一段一条，时间轴取每段波形的真实长度
（不是服务端报的秒数——那个误差是累积的）。文件写在音频旁边、同名 `.srt`，
展开面板里有下载按钮（`actions.subtitle_file()`）——此前它一直在写，
但界面上从来没提过它，于是看起来像没出。


**七条硬约束**，都是「不这么写就会两条路不一致」：

- **分段来自 `actions.speech_segments()`**，也就是自动合成用的那个
  `_build_segments` —— 面板里看到的就是真会合成的那批。这一步会做**一次朗读友好化**
  （`TTS_PREPROCESS=true` 时是一次 LLM 调用，走缓存）。
  `重新拆条` 走 `console.resplit()`（＝`split_for_speech`，纯函数），
  **不会再跑一次朗读友好化**：面板里的文本已经是预处理过的了。
- **「全部合成并保存」走 `actions.run_production(..., segments=...)`**，
  即 `produce(segments=...)` ——写 production 行、量真实时长、出字幕，
  和自动合成**同一条落盘路径**。`segments=None` 时那条路径一字未变。
- **`▶` 生成本段不写台账**：`dna.tts.console.preview_segment()` 只回 wav 字节，
  界面用 base64 data URL 就地播。它免费且无副作用，写一行成功/失败记录会污染
  那一格的历史。它调的是 `provider.synthesize()` 而不是底层 client——
  「克隆模式不能同时给音色名」那条护栏只有一份。
- **逐段生成的波形会被整篇合成复用**：`produce(..., rendered={段号: wav})` →
  `TTSServiceProvider.synthesize(rendered=...)`，那些段跳过客户端调用，但**照样**
  走 `_join` / `build_cues` / 落盘。唯一代价是复用的段没有服务端产物路径，
  `artifacts` 少几条（本来就允许拿不到）。
  `rendered` 的下标按**滤掉空段之后**的位置算，与服务端的编号一致——错一位的表现是
  某一段的音频跑到别的段上，每段单独听都是好的，整篇听起来像乱序。
- **改过的文本先写回稿子再写音频行**：`produce/service.py::save_script_text()` →
  `documents.replace_spoken()`（保留 front matter，只换 `SPOKEN_MARKER` 之后的正文）
  → `record_production(calls=0, instructions="人工校对（TTS 操作台）")`。
  顺序反了的话，音频那一格的前置稿子还是 LLM 那一版。
  **长文案直接拒绝**（`ValueError`）：它的稿子按发言人分轮存在 JSON 边车里，
  拉平成一段纯文本会把一场访谈变成一个人念完全部。
- **种子只在重掷之后才发**：`voice_controls.reroll_seed(index, reroll)`，
  没重掷过返回 `None` → payload 里没有 `seed` → 与自动合成同一版。
  重掷后 `BASE_SEED + index + 7919 * reroll`（照抄 TTS 图形界面的算法），
  种子里带段号，否则整篇会一起变成同一个采样偏好，听起来像换了个人。
- **事件标记追加到这一段末尾**，与 TTS 图形界面同一做法。要插在中间就手打——
  为了取光标位置去写一段 JS，坏起来的表现是「点了没反应」。
  服务端 `events: true` 是默认值，`[pause:400ms]` 今天就已经被解析；
  `clean_for_speech` 不吃这个标记（`_MD_LINK` 要求 `](…)`）。

换参考音频时 `ref_text` 会被清掉、退回 `x_vector_only` 克隆：参考文本只对录它的
那一段音频成立，套到别的音频上就是让 ICL 去对齐一段没说过的话。这条规则和
「克隆模式下 `speaker` 放绝对路径、不带音色名」都住在
`frontends/nicegui_app/voice_controls.py::voice_from()`（纯函数，可单测），
顶部的统一配置与每段的「单独配置」是**同一个类的两个实例**。

上传的参考音频经 `console.save_ref_audio()` 落到 `data/ref_audio/`：文件名过 slugify
（名字来自别人的机器），**重名不覆盖**——覆盖会悄悄换掉别的产物正在用的那把音色。

## 5bis · 三种发声模式（音色设计在内）

操作台顶部那组单选就是服务端的三种 `mode`，`mode` 一路是字符串传到
`/tts/synthesize`，所以**加一种模式不需要动 DNA 的后端**：

| 模式 | 服务端 `mode` | 必填 | 说明 |
|---|---|---|---|
| 内置音色 | `custom_voice` | 音色名 | 服务端 `/voices` 给的那批；「语气指令」只调语气 |
| **音色设计** | `voice_design` | **音色描述** | 没有现成音色时用自然语言现造一个声音；描述写在「语气指令」那个框里 |
| 克隆参考音频 | `voice_clone` | 参考音频 | 默认发声方式，见第 3.5 节 |

三条前置条件由服务端 `SynthRequest._check_consistency` 强制，缺一个就是 422。
合成一段要等几十秒、整篇要几分钟，所以 `voice_controls.voice_problem()`
**在点下去之前**就把缺的那一项说出来：

- `voice_design` 没有 `instruct` → 「音色设计要先写音色描述」
- `voice_clone` 没有 `ref_audio` → 「克隆模式要先选一段参考音频」
- `custom_voice` 没有音色名 → 「内置音色模式要先选一个音色」

另外两条互斥规则也在 `voice_from()` 里（纯函数，可单测）：
`voice_design` **不能带 `ref_audio`**（服务端明确报错，不做静默忽略），
且从克隆/设计切回内置音色时**不能拿 `base.speaker` 兜底**——克隆配置下那里放的是
一条 wav 路径，当成音色名送去合成必然失败。

**同一段描述每次生成不完全一样**：`voice_design` 是按描述采样出来的声音，
不是一个固定音色。要一整篇听起来是同一个人，别在整篇里混用设计与内置音色；
真要稳定复用，先设计一段满意的，把它录下来当参考音频走克隆。

### 交接给 TTS 图形界面的那条路已删除

从前操作台右上角有个「打开完整 TTS 界面（音色设计等罕用功能）」，它 POST
`/gui/handoff` 拿 token、新标签页打开 TTS 模块自带的界面、这边每 4 秒轮询收产物。
**整套已删**（`open_tts_workbench` / `collect_tts_handoff` / `import_tts_handoff` /
`_watch_handoff`），原因两条：

1. 那是**另一个进程的另一套界面**，一关窗就整体退出（实测
   `forrtl: error (200): program aborting due to window-CLOSE event`），
   而它写盘的位置不受 DNA 台账管——同一台机器上两个界面各管一半。
2. 它唯一还独占的功能是音色设计，而那只是 `mode` 的第三个取值，
   在操作台里就是多一个单选按钮。

`tts/client.py` 的 `handoff()` / `handoff_state()` 留着——它们是服务端 API 的镜像，
删了下次要接回来还得重写；但**没有任何界面再调它们**。

## 6 · 朗读友好化（唯一的 LLM 调用）

`tts/preprocess.py`，**一次**调用解决四类问题：

| 类别 | 例子 |
|---|---|
| 不易读的写法 | `RTX 4060` → `RTX 四零六零`；`3.5x` → `三点五倍`；`P(A\|B)` → 念得出来的说法 |
| 多音字 | 会读错时换成**完全同音**的另一个字；人名/地名/产品名一律不动 |
| 断句 | 按朗读的呼吸停顿加标点、拆长句 |
| 自然度 | 该停的地方插 `[pause:400ms]`（TTS 模块的确定性停顿标记） |

**为什么不用规则表**：规则必须穷举，而它永远穷举不完 —— 每来一个新缩写、新公式
就要改代码，而且会互相干扰（把 `4060` 改成「四零六零」之后，`4060 Ti` 又不对了）。
所以规则化的部分只留 `clean_for_speech`（去 Markdown 与网址，那是格式清洗，
不是语言判断）。

**三条护栏**（预处理绝不能挡住音频）：

1. 调用失败、超时 → 退回清洗后的原文，记一行日志
2. 改写后长度偏离原文 0.6~1.8 倍之外 → **丢弃**。那说明模型自己续写或大段删除了，
   而音频里多念一段不存在的内容，比读音不完美严重得多
3. `TTS_PREPROCESS=false` 彻底关掉

调用走 LLM 缓存：同一段稿子重做音频时，这一次是免费的。

**这次调用发生在本项目，不在 TTS service 里** —— 两件事别混：

| | 谁调 LLM |
|---|---|
| **TTS service**（`Agent_TTS_Module`） | **从不调用**。它是纯 TTS：给文本、给参数，回音频。instruct、停顿标记这些都由调用方给 |
| **本项目的音频生成流程** | 调一次（朗读友好化），因为「什么写法念得顺」是文案层的判断，不是合成器该管的事 |

所以「TTS 不调 LLM」和「合成音频前有一次 LLM 调用」不矛盾：前者说的是那个服务的
职责边界，后者是本项目在把文案交出去之前自己做的准备。台账里音频仍记 `calls=0`
（合成本身不计费），预处理那一次计入 LLM 缓存统计。

## 7 · 界面上的动态效果

音频合成时右下角一个浮窗（`frontends/nicegui_app/audio_progress.py`）：
**秒表 + 进度条 + 已产出秒数 + 按实测速度推的剩余时间**。

一个静止的转圈图标只能回答「在跑吗」，而且回答得并不可信 ——
卡死的页面上转圈照样在转（那是 CSS 动画，不是程序还活着的证据）。
秒表在走才说明事件循环还活着；进度条按「已完成段/总段」推进才是真实进展。

服务报出段数之前保持**不确定态**，而不是画一个 0% —— 0% 会被读成「卡在开头」。

## 8 · 命令

```bash
dna doctor                          # 含「TTS 服务」一项：在线 / 会自动拉起 / 缺哪项配置
dna tts                             # 探活（会自动拉起）+ 列音色，不合成
dna tts --say "一句话" -o out.wav   # 真的合成一次，报 音频/耗时/RTF
dna produce <id> --kind narration_audio
dna gui                             # 展开口播格 → 「合成音频」或「TTS 操作台」
```

换到 4060 那台机器时：那边起服务（`python -m agentic_tts.cli serve --host 0.0.0.0`），
这边把 `TTS_SERVICE_URL` 指过去。**远程地址不会自动拉起**，doctor 会明说这一点。

## 9 · 已知限制

| 限制 | 说明 |
|---|---|
| `RTF_ESTIMATE = 2.5` 只是数量级 | 那是 0.6B OpenVINO 核显上量的；服务侧换 1.7B 后 CPU 实测 ≈13，**按钮上的预估会少报五倍**。准确值来自合成时逐段回报的进度。这个倍率**应当从配置读、一处定义**，见 [issues/009](issues/009-tts-speaking-rate.md) |
| 音色设计不可复现 | 同一段描述每次采样出的声音不完全一样；要稳定复用就录下来当参考音频走克隆 |
| 服务重启会丢正在跑的那一条 | 已完成的段落仍在服务端 outputs/ 里 |
