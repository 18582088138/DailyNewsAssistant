## 提示词正文不在这份文档里

**唯一来源是 `config/prompts/`**，一个任务一个 Markdown 文件。
本文只记**为什么这么写**：调优记录、实测对照、踩过的坑。
下面各节引用的提示词片段是**摘录**，正文以 `config/prompts/` 为准。

```
config/prompts/
├── README.md                        改法、{{占位符}} 与 ## @分块 语法
├── summarize.md · translate.md · trend.md
├── shortvideo.{zh,en}.md · narration.{zh,en}.md
├── longform_outline.md · longform_section.md
├── tts_preprocess.md
└── _shared/                         被多个任务引用的片段
    ├── professionalism.{zh,en}.md   三种文案共用的写作要求
    ├── instruction_block.{zh,en}.md
    └── language_directive.en.md
```

调一句话之后的验证顺序（详见 `config/prompts/README.md`）：

```bash
dna prompt --list                       # 各任务读哪些文件
dna prompt <id> -t narration            # 看真正发出去的提示词（**零费用**）
dna prompt <id> -t narration --run      # 真机跑一次看产物（**计费**）
dna produce <id> -k narration --force   # 满意了再正式生成
```

`dna prompt` 看到的提示词与 `dna produce` / 工作台点「重做」发出去的**逐字节相同**：
两条路都走 `dna.produce.service.generate_text()`，只有注入的 provider 不同
（`src/dna/produce/prompt_lab.py`、`src/dna/llm/capture.py`）。
所以在调试台里验证过的提示词，在应用里必然生效——这一条有单测护着
（`tests/produce/test_prompt_lab.py::test_render_matches_what_produce_sends`）。

**改完会 LLM 缓存 miss，这是对的**：缓存键是完整 messages，改一个字就换一个键，
于是拿不到旧答案。反过来说，没改而重跑一次是免费的。

## 零、通用约束

**所有节点共同遵守：**

| 约束 | 原因 |
|---|---|
| 打分类字段必须写 `ge` / `le` 与 `description` | 不写的话不同模型会自己发明量纲——实测同一输入 qwen3.5:9b 给 95.0、qwen2.5:3b 给 3.0（[issue 002](issues/002-small-model-echoes-json-schema.md)） |
| 提示词明确「给数据，不要照抄 Schema」 | 小模型会把 JSON Schema 原样返回 |
| 单节点失败**降级不抛异常** | 日报无人值守跑，一条翻车不该让整期作废 |
| 提示词构建是**纯函数** | 单元测试断言「我们问了什么」，不花钱、不飘 |
| 相同请求命中磁盘缓存 | 调提示词时只有真正改动的那部分重新计费 |

**测试策略**：断言提示词构建与响应解析，**不断言模型说了什么**。
模型输出质量在阶段验收时人工看一次。

## 一、summarize —— 条目摘要

**提示词**：`config/prompts/summarize.md`　**代码**：`src/dna/pipeline/summarize.py`
**调用次数**：每个事件一次

### 输入

```
标题：{title}
（另有 N 家媒体报道同一事件：{其它标题}）      ← 仅多源时出现
正文：{text[:3000]}
```

正文截到 **3000 字**。3000 字足够写出准确摘要，再多只是线性增加 input token 费用；
一期几十条，差别很可观。

正文为空时改为：

```
（正文抓取失败，只有标题可用——请基于标题写，不要编造细节）
```

**这句不能省。** 不说的话模型会自信地补出一段看似合理、实则凭空捏造的内容，
而它会原样印进日报，读者无从分辨。

### 输出结构

```python
class SummaryOut(BaseModel):
    summary: str = Field(min_length=10, max_length=400,
                         description="1~2 句中文摘要，只陈述原文事实，长度按提示词的要求")
    tags: list[str] = Field(max_length=4, description="1~4 个主题标签")
```

顺手要 `tags`：日报要按主题分组，同一次调用里让模型打标签比事后再调一次便宜得多。

### 关键指令

1. **字数 {{lo_chars}}~{{hi_chars}} 字，这是硬指标**（取自 `profile.summary_chars`，
   与程序验收用的是同一个数）
2. **信息要完整**：原文讲了几件事就都要覆盖到。既讲模型发布又讲第三方量化方案的
   文章，两件事各占一句，不要只写前一半
3. **挑最有价值的指标**。优先级：
   核心事实 > 架构关键参数（总参/激活参/上下文长度）> 能力对比结论 >
   次要细节（文件体积、依赖版本、硬件型号）> 榜单排名与得分
4. 每句都要带数字或专有名词，不出现只有形容词的句子
5. 只写原文里有的，**不做推测、评价或补充背景**（「这验证了……」「标志着……」一律不要）
6. 不要用「本文介绍了」「据报道」开头，也不要把标题重述一遍
7. 保留产品名、公司名、版本号、性能数字
8. 末尾带一份**交稿自查清单**——把硬指标再列一遍让模型逐条对

### 为什么要给指标排优先级

「1~2 句」是硬约束，装不下所有数字，所以**取舍规则必须写进提示词**。不写的话
模型按原文出现顺序取，而技术文章的开头往往是模型体积、依赖版本这类次要细节；
真正决定这条资讯价值的参数可能在第三段。

实测对照：模型自选写了「原生 8-bit 精度模型文件 167GB」，而人工撰写的参考摘要
在同一位置写的是「激活参数 13B」——后者才是读者判断要不要点开的依据。

### 失败处理

**降级为用标题当摘要**，`degraded=True`。标题本身就是一句话摘要，足以让读者判断
要不要点开；因为一次 API 抖动就把真实资讯从日报里删掉，代价大得多。

### 调优记录

| 日期 | 改动 | 原因 |
|---|---|---|
| 2026-09-02 | 初版 | 真机验证：DeepSeek 输出稳定，技术术语与数字保留完好 |

## 二、translate —— 双语翻译

**提示词**：`config/prompts/translate.md`　**代码**：`src/dna/pipeline/translate.py`
**调用次数**：每 10 条一次（批量）

### 输入

```
[id: {entry_id}]
标题：{title_zh}
摘要：{summary_zh}
```

**输入是已写好的中文摘要，不是原始正文。** 译摘要比用英文重写一遍便宜得多，
而且保证中英两版说的是同一件事。

### 为什么带 id

要求模型原样返回 id，按 id 对回原条目。**只靠顺序对齐是危险的**：模型漏译一条，
后面全部错位——第 3 条的英文安到第 2 条头上，中英两版说着不同的事，
而且**不会报任何错**。

模型返回未知 id 时丢弃；漏译的条目不出现在结果里（调用方据此知道哪些没译成，
而不是拿到一个填了空串、看起来完整的字典）。

### 关键指令

1. Translate meaning, not words
2. **产品名、公司名、版本号、指标原样保留**（GPT-4o 仍是 GPT-4o；通义千问 → Qwen）
3. 标题保持 headline 风格：不加句号，不硬塞 "The"
4. 不增不减信息

### 批量大小

10 条。太大容易超出输出长度并让模型**静默漏译**——而漏译是看不出来的。

### 失败处理

返回空字典，中文版照常可用。英文版是附加产物，它失败不该让中文版也发不出去。
整段翻译（趋势综述）失败返回 `None` 而不是原文——把中文塞进英文版比缺一段更糟，
读者会以为是排版事故。

### 调优记录

| 日期 | 改动 | 原因 |
|---|---|---|
| 2026-09-02 | 初版 | 真机验证：`2TP×4USP`、`XPU Kernel`、`Layer-wise Offloading` 均原样保留 |

## 三、trend —— 当日主线提炼

**提示词**：`config/prompts/trend.md`　**代码**：`src/dna/pipeline/trend.py`
**调用次数**：整期一次

### 输入

```
今日条目（按重要性排序）：

1. {title}
   {summary}
2. ...
```

带编号：模型可以说「其中第 2、5 条同属一个方向」，比复述标题精炼。
顺序即重要性，模型会自然更重视靠前的条目。

输入是**已压缩的摘要**，不是原始正文——综述要的是跨条目共性，喂全文只会增加成本
并让模型被细节淹没。

### 关键指令

1. 找出**跨条目的共性主线**，150~250 字
2. 可以有判断和观点，但必须建立在给出的条目上，**不引入外部信息**
3. **不要逐条复述**——那是下面的条目要做的事

第 3 条不写的话，模型会写成一段「今天有五条新闻，分别是……」的目录，
放在开头毫无价值。

### 条目数门槛

少于 **4 条不调用 LLM**。两三条新闻谈不上「趋势」，硬写只会得到一段把标题
重述一遍的废话，而且还要花钱。

### 失败处理

返回 `(None, [])`。日报没有综述照样成立——它是加分项不是必需品。

### 调优记录

| 日期 | 改动 | 原因 |
|---|---|---|
| 2026-09-02 | 初版 | 真机验证：5 条输入下正确提炼出「效率与成本优化」这条共性主线，未逐条复述 |

## 三 bis、单篇文案（P3.5）

### 第一要求是信息密度

时长是固定的（平台限制，而且发布时视频还会**加速播放**），所以稿子的成败在于
**同样的秒数里装进多少事实**。「不要白话」不是用词问题——一句没有数字、
没有专有名词的话，就是白占了那两秒。

共用的约束写在 `config/prompts/_shared/professionalism.zh.md`（经 `script_builder.rules_for()` 读入）：

> 1. **信息密度优先，这是第一要求**。每一句都必须携带至少一个具体信息点——
>    一个数字、一个专有名词、一项能力、或一个明确结论。写不出信息点的句子直接删掉
> 2. **使用准确的技术术语**。不要用「非常厉害」「大幅提升」「迈上新台阶」替代具体指标
> 3. **模型名、版本号、benchmark 名称、数值必须与原文完全一致**，不得改写或近似
> 4. 不确定的技术细节**宁可不写**
> 5. **禁止出现**：填充语（「让我们一起来看看」）、单独占一句的过渡句
>    （「这意味着什么」）、第一人称主观表达（「我最关注的是」）、
>    用形容词堆出来的结尾（「让企业级应用不再需要巨额硬件投入」）
> 6. 面向懂技术的听众，不解释什么是大模型

第 5 条是逐条点名的，不是笼统地说「不要白话」——**笼统的禁令模型无法执行**。
这四类都是从真机产出里挑出来的实际问题，其中「这意味着什么」是提示词里的
结构提示被原样写进了稿子。

**输入用正文而不是摘要。** 摘要的任务是百字上下的快速浏览，技术细节已经被
压掉了；拿它写口播，模型手里除了几句结论什么都没有，只能用形容词填满一分钟。

正文上限 **6000 字**，是摘要节点的两倍：摘要每条都跑（一期几十条，上限乘以条目
数），文案单篇按需跑（宽一点只影响这一次调用）。3000 字不够——实测一篇 4069 字
的技术稿，被切掉的最后 1069 字里有采样参数和一条关键局限（官方没给 Jinja chat
template，「能跑」和「跑对」是两回事），而那正是「必须说局限」要用的料。

### 短视频文案（`profile.shortvideo_chars`，默认 200~250 字）

关键约束：**覆盖文章主干，不是单点深挖**。
- **第一句必须是事件本身**：谁、发布/开源了什么、叫什么名字（带完整版本号）。
  不用悬念或设问开场——观众得先知道在说什么
- 之后按「最硬的指标 → 关键参数 → 能力亮点」往下推，**每句换一个新事实**
- 可以用短句和感叹句制造节奏，但**每个短句后面必须紧跟具体数据**
- 结尾固定用 `profile.cta_line`

输出结构：主标题（**写事件本身**，含产品名/型号）+ 副标题（**堆亮点与意义**）+ 正文。
字数上限只在提示词里写（≤15 / ≤20），**不写进 schema 的 description**——
那会变成第二个来源，模型同时看到两个数字就两个都不当真。

> **这条约束改过一次。** 初版要求「一条视频只讲一个点」，产出技术上正确却
> **没把文章讲清楚**：观众听完知道 UD-Q8_K_XL 的困惑度没变，却不知道这是哪个模型、
> 发布了没有。人工撰写的参考稿在 30 秒里放了六个事实，每句一个。

### 口播文案（`profile.narration_chars`，默认 400~800 字）

关键约束：**必须有技术深度**——这是它区别于短视频稿的全部理由，只把结论念一遍
是不合格的。要求说清方法、关键数字、以及这些数字为什么成立；
**信息要覆盖原文主干**，不要因为展开细节而漏掉另一半内容。

原文提到局限或代价时**必须说**，只讲好处的稿子没有可信度。
结尾**落在具体建议或具体数字上**（「128GB 以下建议直接用 API」），
不要用形容词收束，然后接 `profile.cta_line`。

同样输出主副标题——1~2 分钟的稿子也是发到平台上的视频，标题栏一样要填。

### 长文案（5~15min，专题/访谈）

**分三步，不能一次生成**：3000~4000 字远超单次输出的可靠范围，硬要一次生成，
模型会在中途丢失结构、重复论述、越写越水——而「不要白话」恰恰是核心要求。

1. **提纲**（1 次调用）：4~8 节，每节带要点与目标字数。要求「**必须有一节讲局限**」，
   并禁止规划「总结回顾」这种把前面重说一遍的节
2. **逐节展开**（每节 1 次）：带上一节结尾做衔接。分段生成最容易在接缝处断裂——
   上一节刚说完某个数字，这一节又从头介绍一遍同一件事
3. **拼装**，不做全文重写（太贵，收益有限）

访谈模式额外约束：**主持人只提问、追问、转场，不讲技术内容**；
**明确禁止互相吹捧**（「您说得太好了」占时长、没信息，一听就假）。

### 长度控制：字数是验收标准，秒数只是参照（2026-09-09 改）

配置在 `config/profile.yaml`：

```yaml
summary_chars: [80, 100]        # 条目摘要
shortvideo_chars: [200, 250]    # 短视频文案
narration_chars: [400, 800]     # 口播文案
```

**这三个数字同时做三件事**：写进提示词、写进交稿自查清单、用于程序验收
（`core/length.py::char_feedback`）。改配置一处，三处一起动。

英文版折算成**词数**（约为字数的 0.39 倍，`duration.unit_window`）：
一个英文词的口播时长约等于两个半汉字，按字符 1:1 折算英文稿会长出一倍多。

`estimate_seconds` 退为参照：记进产物、显示在界面上，**不参与验收**。

#### 为什么从秒数改成字数

先前提示词说字数、验收看秒数，两个单位之间的换算比例**随中英混排程度浮动 50%**：

| 实测产出 | 字数 | 秒数 | 折算 |
|---|---|---|---|
| 混排（含 LLM-as-a-Verifier / Terminal-Bench 等） | 228 | 31.1s | 7.3 字/秒 |
| 中文为主 | 168 | 28.8s | 5.8 字/秒 |
| 纯中文 | — | — | 4.5 字/秒 |

后果是双向的，而且都不报错：

- 一份 250 字的稿子，中文多时估到 43 秒 → 超时回炉，反馈是「**删掉 N 字**」，
  与提示词里的 200 字下限**直接打架**，第二稿两边都不满足
- 一份 168 字的稿子，秒数落在 25~35 内 → **静静通过**，比提示词的下限少 32 字，
  程序一声不响

实测：一次 shortvideo 生成耗时 312 秒、两次调用，就是回炉循环在跟提示词对抗。

改成字数之后，提示词要求的单位和程序检查的单位是同一个，差值是**减法**——
不再需要按密度换算（`observed_chars_per_second` 那套自校准逻辑随之退役）。

#### 混排密度系数还在，但只用在退路上

`prompt_char_budget`（4.5 × 1.5 ＝ 6.75 字/秒）现在只在**没给字数配置**时用来
从秒数推一个窗口，生产路径一律走配置。它的实测依据保留在下面，
因为「按纯中文 4.5 折算会系统性少要三分之一」这个坑还成立：

```
人工撰写的参考稿   199 字符 → 27.8 秒 ＝ 7.2 字符/秒
本系统生成的稿子   185 字符 → 25.8 秒 ＝ 7.2 字符/秒
```

#### 摘要也有长度检查了（2026-09-09 新增）

先前**完全没有**：`SummaryOut.summary` 只有 `max_length=400`，写多长都通过。
实测 7 篇摘要在要求 80~100 字的情况下产出 107~163 字，最多超 63%。

现在 `summarize_cluster(chars=...)` 会数字数并回炉，但**只给 1 次**
（`summarize.MAX_REWRITES = 1`，文案是 2 次）：摘要每条都跑，一期几十条，
回炉一次就把整期成本翻倍。

#### schema 的 description 里不再写字数

`description` 会随 JSON Schema 注入提示词，写了字数就等于**第二个来源**。
先前 `SummaryOut.summary` 的 description 写着「60~120 字」而提示词说 80~100，
主标题的 description 写着「≤14 字」而提示词说 ≤15——模型同时看到两个数字，
两个都不当真。现在字数只在提示词里出现一次。

## 四、不用 LLM 的节点（刻意的）

| 节点 | 为什么不用 LLM |
|---|---|
| `clean` | 归一化与样板剥离是确定性文本处理，用 LLM 又慢又贵还不稳定 |
| `dedup` | SimHash 与向量相似度是数值计算，LLM 判重既贵又会飘 |
| `score` | **可解释**（知道该改哪）、**稳定**（同输入同分，排序不抖）、**免费**。LLM 打分每次都飘，日报排序跟着抖，而排序本身不需要语言理解 |

LLM 更适合做「必须理解内容」的活（摘要、综述），排序和判重可以用信号量化。

## 五、费用分界

```
clean → dedup → score  │  summarize → translate → trend
──── 免费，随便跑 ────  │  ──── 每次运行都计费 ────
```

`dna digest --dry-run` 停在分界线上：先看清单，确认选题对了再花钱。

**实测成本（2026-09-02，DeepSeek）**：5 条日报 = 6 次调用 / 10.7 秒；
加英文版 = 8 次调用。第二次跑相同输入 = 0 次调用 / 0.1 秒（全部命中缓存）。

## 英文版与修改指令（2026-09-06）

### 英文写作要求是**重写的，不是翻译的**

`config/prompts/_shared/professionalism.en.md` 与中文那份是同一套要求，但逐条用英文重写。

理由：它是**给模型看的指令**，不是产物。指令用目标语言写，模型遵守得明显更好；
而且「白话」「套话」这些词在中文语境里的具体所指，直译过去会变成空泛的
"avoid vague language"——等于把最要紧的那条规则说没了。

### 英文的字数预算不放大

`prompt_char_budget(seconds, lang="en")` **不乘** `MIXED_COPY_CHAR_FACTOR`。

那个 1.5 的系数量的是「中文字数 vs 中英混排稿的实际字符数」，
而英文稿的单位本来就是词，不存在这个折算。照样乘 1.5 会让英文稿超长 50%，
这正是实测反馈「英文输出的文本量太大」的来源之一。

| | 30 秒的预算 |
|---|---|
| 中文 | 202 字（135 × 1.5） |
| 英文 | 78 words（30 × 2.6，不放大） |

### 回炉反馈用稿子自己的语言

给英文稿发中文的「请删掉约 40 字」，模型有相当概率**改回中文输出**——
这一层的输入输出语言应当一致，否则回炉反而把稿子毁了。
差值的单位也随语言走：中文数字符、英文数词，混用会得出
「上一稿 900 字符 → 请删掉 300 words」这种自相矛盾的指令。

### 长文案：每一节都要重复一遍语言声明

长文案是**分十几次调用**拼起来的，每节都是独立请求。
只在提纲那次说一句「用英文写」，后面几节的模型看不到那句话，
会跟着中文原文一起滑回中文——拼出来是中英夹杂的半成品，而这时钱已经花完了。
`language_directive(lang)` 因此出现在提纲与每一节的提示词里，这不是冗余。

### 修改指令接在末尾

`instruction_block(instructions, lang)` 把人写的额外要求接在提示词**最后**：
后出现的指令权重更高，而这段的用途正是覆盖前面的默认要求。

没有额外要求时返回**空串**，提示词与不带这个功能时逐字相同——
否则每篇都会因为多一个空标题而错开 LLM 缓存，白花一轮钱。

### 英文总结要更短

`config/prompts/translate.md` 第 3 条从「与原文长度相当」改成**至多 45 词**，
`TranslatedEntry.summary_en` 的 `max_length` 从 800 收到 400。

上限是这条规则的最后一道防线：提示词是建议，schema 是约束——
放着一个两倍于目标的上限，等于告诉模型写到 800 也算合格。

压缩只许砍虚词与连接词，**原文里的每一个数字、模型名、benchmark 都必须留着**。
