# 017 · 字幕显示的是改写稿，且一段一条太长

**状态**：已修复（`tts/cue_split.py` + `tts/vad.py` + 数据流改动）
**发现**：用户实测反馈，2026-10-05

---

## 现象 / Symptom

用户的原话：

> TTS 中的字幕更像是 TTS 文本而不是字幕，长度不合理，显示的内容也不合理。

具体两件事：

1. **太长**：`tts/segment.py` 的 `DEFAULT_MAX_SEGMENT_CHARS = 120`，而字幕是
   **一段音频一条** —— 于是一条字幕可能挂十几秒、显示上百字。
2. **内容是改写稿**：字幕文本取自 `piece.text`，而那是经过一次 LLM
   「朗读友好化」的稿子。

## 判定 / Diagnosis

### ① 字幕文本是给耳朵的，不是给眼睛的

```python
# tts/service.py:205
spoken.append((_wav_seconds(body["wav"]), piece.text))   # piece.text = 改写后
```

`tts/preprocess.py` 的 LLM 调用会做这些改写：

| 改写 | 例子 | 显示出来的后果 |
|---|---|---|
| 多音字换同音字 | 「模」型 → 换成同音的另一个字 | **错字** |
| 缩写/公式改读法 | `RTX 4060` → 「RTX 四零六零」 | 啰嗦但不算错 |
| 加合成指令 | `[pause:400ms]` | 由 `cue_split.strip_markup` 兜住 |

而**原文案在 `produce/audio.py` 里现成可得**（`prepare_for_speech(text)` 的入参），
只是没被传下去 —— `PreparedSpeech` 只带出了改写后的 `text`，
`clean_for_speech` 算出的原文用完就丢了。

### ② 顺带查清的一个坑：不能按字数比例映射

`tts/preprocess.py:54-55`：

```python
_MIN_RATIO = 0.6
_MAX_RATIO = 1.8
```

改写前后长度允许 **0.6~1.8 倍**浮动，所以「按字数比例把原文映射到朗读稿的时间轴上」
**必然错位**。这条否掉了最省事的做法，只能做**条数配对**。

## 修法 / Fix

### 数据流：让原文活下来

| 文件 | 改动 |
|---|---|
| `tts/preprocess.py` | `PreparedSpeech` 增加 `source` 字段（= `clean_for_speech` 的输出） |
| `tts/base.py` | `SpeechSegment` 增加 `source`；`AudioClip` 增加 `piece_cues` |
| `produce/audio.py` | 把原文按段挂到每个 `SpeechSegment` 上 |

`source` 与作者写的**逐字对应**（那一步只删 Markdown 标记，不改字），
所以它就是「修改前的文案」。

### 切分：条数配对，不按比例

新增 `tts/cue_split.py`（纯函数）：

```
① 朗读稿按标点与字数上限切 → M 条     ← 决定该有几条字幕
② 理论边界 = 累计字数比例 × 时长
③ 边界**吸附到最近的真实停顿**（同一个停顿不会用两次，且保持单调）
④ 原文切成**恰好 M 条**（按累计字数找最近的单元边界，不劈词）
⑤ 配对输出
```

时间轴之所以在**朗读稿**上算：音频是按它合成的，只有它与时长成正比；
而文本取**原文**。**两者无法同时完美**，这里选文本优先，
代价是偶尔偏几十毫秒 —— 比显示错字轻得多。

### 停顿从哪来：自己写一个能量法 VAD

新增 `tts/vad.py`。**没有引入任何依赖**：`pyproject.toml` 的 `tts` 组只有
`httpx`，注释明说「波形拼接用标准库 wave，连 numpy 都不需要」，
为几十秒的干净音频拉一个 onnxruntime 不划算。

能量法在这里够用的理由：输入是 **TTS 刚合成出来的**音频，不是现场录音 ——
没有背景音乐、没有环境噪声、没有混响尾巴，静音段真的接近零。

两个实现细节值得记：

- **语音电平取高分位，不取峰值**：一个爆破音就能把峰值抬高一个数量级，
  用峰值当基准会把整段判成静音；
- **位深不认识时抛错，不返回空样点**：返回空会让停顿检测报「整段没停顿」，
  那看起来像「音频本来就连贯」，而实际是读不了 —— 两种情况必须能区分。

### 逐段字幕一起落盘

用户要求「字幕文件和音频文件一样，一起落盘」。音频的逐段副本早就落了
（`AudioClip.pieces` → `seg_001_narrator.wav`），字幕却只有整条那份。
现在 `fetch_artifacts` 会顺带写 `seg_001_narrator.srt`：

- **同名同扩展名**，看一眼文件夹就知道谁配谁；
- 逐段字幕的时间**从 0 起算**（描述这一段自己），与整条的累积时间轴不同 ——
  想单独替换某一句时，带着整条偏移反而没法用。

## 实测 / Measured

真实合成产物（7 段、9~13 秒/段）上跑新的切分：

| 段 | 时长 | 检出停顿 | 切出条数 | 平均条长 |
|---|---|---|---|---|
| seg_001 | 10.88s | 4 | 4 | 2.72s |
| seg_002 | 9.44s | 5 | 4 | 2.36s |
| seg_003 | 12.94s | 4 | 4 | 3.23s |

⇒ 10 秒左右的一段从「1 条」变成「4 条」，平均 2~3 秒一条。
**能量法在真实 TTS 音频上确实找得到停顿**（每段 2~6 个），这一条原本是未验证项。

## 回归用例 / Regression

- `tests/tts/test_vad.py` —— 停顿检测、分位数抗爆音、位深与声道、读不了要抛错；
- `tests/tts/test_cue_split.py` —— **条数必须精确等于 n**、切分不增删字符、
  停顿每处只用一次、**显示原文而非朗读稿**、时间轴单调且有界；
- `tests/tts/test_subtitle.py` —— 逐段字幕从 0 起算、整条时间轴算进段间静音、
  文件名与音频同名、SRT 带 BOM、读不了波形也要出字幕；
- `tests/produce/test_service.py::test_piece_subtitles_land_beside_piece_audio`
  —— 端到端：逐段 srt 与逐段 wav 同目录落盘，且内容是原文。
