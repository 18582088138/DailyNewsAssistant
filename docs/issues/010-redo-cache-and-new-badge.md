# 010 — 重做拿回旧答案 · NEW 标识过夜消失

> 状态：✅ **两个都已修复并真机复验**。2026-09-06 用户实测反馈。

---

## A. 重做调了 LLM，内容却一字未变

### 现象

> 「重新生成按钮点击后虽然重新调用了 LLM，但是新生成的内容并没有更新到 GUI 以及 MD 中，
> 相当于重新生成了，但是没有保存。」

### 根因：不是没保存，是**保存了一份一模一样的**

LLM 响应缓存**故意不设过期**，键是 `provider + 模型 + 完整消息 + temperature + max_tokens + json_mode`。
`llm/cache.py` 的模块文档写得很清楚：

> 不设过期时间：同样的输入配同样的输出，正是我们想要的可复现性。
> **需要新答案时用 `temperature` 或提示词的真实变化去错开**，而不是靠缓存失效。

而重做按钮两样都没做：提示词一个字没改，temperature 是构建器里写死的。
于是这一轮里发生的事是——

1. `force=True`，跳过「已存在就返回」的保护 ✅
2. 真的调了 `llm.chat_json(...)` ✅
3. **缓存命中，返回上次那份字节相同的响应** ← 就是这里
4. 文件真的被重写了，内容一字未变
5. 界面刷新，表格重建，展开的面板跟着关掉

从用户角度看：点了按钮、转了圈、面板关了、内容没变 = 「生成了但没保存」。

**这条失效不会报任何错。** 台账里能看出痕迹：

```
summary/zh 版本链
  id=11 258字 redo_of=6   09-03 15:12
  id=6  258字 redo_of=1   09-03 15:10    ← 两次重做，字数一模一样
  id=1  235字 redo_of=None 09-03 13:26
```

### 修复

`force=True` 时构造**不带缓存**的 provider：

```python
provider = None if is_audio else (llm or get_llm(cache=not force))
```

「重做」的字面意思就是要一份不一样的，而缓存的定义是「同样输入给同样输出」——
这两件事本来就不该同时成立。

顺带修掉两个放大这个现象的因素：

- **界面刷新后保持展开**。刷新会重建整张表，展开的面板本来会关掉——
  而那正是最想看新内容的时刻。现在记住 `(文章 id, 产物类型)`，重建后自动展开。
- **新增「修改指令」**（见下），写一句额外要求就自然错开缓存，
  而且能真正引导出想要的变化。

### 真机复验（1 次调用）

```bash
dna produce decef4a4 --kind summary --force
```

| | 内容 |
|---|---|
| 重做前 | …304B参数，8-bit精度，模型文件167GB。Unsloth发布13档GGUF量化版本… |
| 重做后 | …304B参数，8-bit精度，文件167GB，**后训练超越V4-Pro预览版**。Unsloth发布13档GGUF量化… |

内容确实变了，而且新版多带出一个原文里的事实。

## B. NEW 标识过一夜就消失

### 现象

> 「New 标签在界面刷新或重新进入后就会消失，需要一直保留，直至对其进行 LLM 操作。」

### 根因：24 小时的时间窗

判定原本是「**最近 24 小时内导入** 且 一条产物都没有」。
实测台账里 `fe3b7d3c`（「都在问世界模型怎么落地，PixVerse把答案做成了「好玩」」）
导入 47 小时、零产物——按用户的定义它应该一直挂着 NEW，被时间窗清掉了。

**时间窗当初解决的是另一个问题**：37 篇里 32 篇没有任何产物（RSS 存量大多如此），
只看「有没有产物」的话 NEW 会挂在 32 行上，标识就没意义了。
窗口确实压住了泛滥，**但它压错了对象**——它让「昨天粘进来、今天还没处理」的链接
第二天失去标识，而那恰恰是最需要标识的一条。

### 修复：改成看**来源**

```python
if productions:
    return False
return record.via in MANUAL_SOURCES      # {"gui", "inbox"}
```

真正要区分的是来源，不是时间：

| 来源 | 含义 | 该不该挂 NEW |
|---|---|---|
| `gui` / `inbox` | 人特意粘进来 / 投进来的 | ✅ 直到处理为止 |
| `rss` | 自动抓的候选池 | ❌ 从来不挂 |

实测：37 行里 **5 行**挂 NEW，全部是 `via=gui` 且零产物的。
既没有泛滥，也不会因为过了一夜就把待办清空。

`Profile.new_badge_hours` 与 `profile.yaml` 里对应的那一行一并删除——
判定里不再有时间成分，留着就是一个改了没反应的死配置。

### 2026-09-10 第三次改：时间窗以「或」的身份回来

用户实测「从订阅导入的文章都没有 new 的标识」——上面那版按来源判定，
`via=rss` 从来不挂，于是刚导进来的一批和躺了两周的存量长得一模一样，
分不出这次采到了什么。

改法是**加一条或分支，人工投递那条判据一个字不动**：

```python
NEW_WINDOW_HOURS = 24.0

if productions:
    return False
if record.via in MANUAL_SOURCES:         # 人工投递：不看时间，直到处理为止
    return True
return record.first_seen_at is not None and \
       record.first_seen_at >= now - timedelta(hours=NEW_WINDOW_HOURS)
```

**为什么这次可以有时间窗，而上一次不行**：上一次它是唯一判据，所以能把
`fe3b7d3c`（47 小时、零产物、人工粘的）的标识**摘掉**；现在它接在 `or` 上，
只能**加**标识、永远拿不掉，当初否掉它的那条理由不再成立。
纯时间窗仍然是错的——注释里保留了这个区别，因为这条判定已经被改过三次，
下一个人多半还想改第四次。

泛滥的问题由分页兜住（同一轮修的第 2 项）：一页 50 行，
挂 NEW 的只是当天那批，不再是整个 RSS 存量。

## 教训

两条都属于**没有任何报错的失效**，而且都只有真人用起来才会发现：

- A 的每一步单看都是对的（跳过了保护、调了模型、写了文件），
  错的是「调了模型」和「拿到新答案」被默认当成了同一件事。
- B 的护栏本身是对的，只是护错了维度——泛滥要压，但压的应该是「哪来的」，
  不是「多久以前」。

对应的测试都钉在了「意图」而不是「实现」上：
`test_redo_builds_an_uncached_provider` 断言的是传给 `get_llm` 的参数，
`test_badge_survives_any_amount_of_time` 把入库时间推到一年前。
