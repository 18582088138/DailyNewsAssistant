# issue 008 — 文案信息量不够：一个静默的单位错误

> 日期：2026-09-03　状态：已修，真机复验通过

---

## 用户的反馈

> 「目前输出的文案的质量不好……我发布的视频会做一定的加速，调高信息含量，
> 目前你提供的文案，信息量不够，同时没有把文章讲清楚。即便是总结类的文案
> 也应该确保信息的完整性，总结最有价值的信息。」

并给了一份人工撰写的参考稿（DeepSeek V4 Flash 那篇）。

---

## A. 根因不在提示词的措辞，在字数换算 —— 已修

### 先量了一遍，而不是先改措辞

拿到反馈的第一反应是「提示词写得不够好」。但先把参考稿和生成稿都送进
`estimate_seconds` 量了一遍：

| | 字符数 | 估算时长 | 字符/秒 |
|---|---|---|---|
| 人工撰写的参考稿 | 199 | 27.8 秒 | 7.2 |
| 本系统生成的稿子 | 185 | 25.8 秒 | 7.2 |

**两篇长度几乎一样。** 密度也一样。所以问题不是「稿子太短」，
而是同样的秒数里放的事实太少——这一步排除了「加长」这个错误方向。

但顺着这个数字往下看，发现了真正的原因。

### 提示词一直在要更少的字

`target_chars()` 按纯中文 4.5 字/秒换算，于是提示词里写的是：

```
口播正文控制在 112~157 字
```

而实测技术稿 30 秒装得下约 **200 字**——因为 `UD-Q8_K_XL`、
`DeepSeek-V4-Flash-0731`、`Artificial Analysis` 这类标识符**占字符多、占时长少**。

模型很听话地照 112~157 字写完，量出来 25.8 秒，**落在 25~35 秒区间的下沿**：

- 验收通过 ✅
- 回炉重写不触发 ✅
- 信息量少掉三分之一 ❌
- **没有任何环节报错** ❌

这就是「信息量不够」的机械原因。措辞再怎么改，字数上限压在那里，
稿子就装不进更多事实。

### 修复：把「物理量」和「给模型的预算」分成两个函数

```python
def target_chars(seconds):          # 物理量：estimate_seconds 的严格逆运算
    return int(seconds * CHARS_PER_SECOND_ZH)

def prompt_char_budget(seconds):    # 要告诉模型写多少字
    return int(target_chars(seconds) * MIXED_COPY_CHAR_FACTOR)   # ×1.5
```

系数 1.5 来自上表的实测（7.2 ÷ 4.5 ≈ 1.6，取 1.5 保守）。
**验收仍然只走 `estimate_seconds`**——放大只作用于提示词，不放松标准。

结果：

| | 25~35 秒对应的字数 |
|---|---|
| 改前（4.5 字/秒） | 112~157 字 |
| 改后（混排密度） | **168~235 字** |
| 参考稿实际 | 199 字 |

### 顺带修掉回炉环节的同一个错误

`length_feedback()` 也在用固定的 4.5 字/秒换算「该删多少字」。
一篇 8 字符/秒的技术稿超时 10 秒，它只会说「删 45 字」，
而实际需要删 80 字——**第二稿仍然超时，那次调用白花**。

改成按上一稿自己的密度换算：

```python
rate = observed_chars_per_second(chars, seconds)   # chars / seconds，实测
delta = int((seconds - high) * rate)
```

比任何预设系数都准，因为它量的就是这篇稿子自己的中英比例。密度随题材变化很大
（纯中文资讯约 5 字符/秒，堆满量化档位名的技术稿接近 9），预设常数必然对一半
的稿子算错。

### 教训

**「同一个量不要有两种单位」的下一层：两种单位都对，但用错了场合。**

[issue 007-C](007-p35-workbench.md) 修的是「目标按字符数推、验收按秒数算」，
当时的结论是「统一到时长空间」。这次发现统一之后仍然错——因为从时长换回字数
时用了**纯中文语速**，而稿子是中英混排的。

真正的教训是：**换算系数必须来自实测，不能来自定义。** 4.5 字/秒是「中文播报
语速」的定义值，它对纯中文稿成立；一旦稿子里有三成英文，这个系数就不再是那个
场景的答案了。现在 `MIXED_COPY_CHAR_FACTOR` 的注释里直接钉着那两行实测数据。

## B. 短视频「只讲一个点」是错的要求 —— 已改

### 现象

初版提示词写的是：

> **一条视频只讲一个点**。从原文里挑最有说服力的那一个，围绕它讲透，不要罗列

产出（26 秒）：

> DeepSeek-V4-Flash 的量化有个反直觉结论：Unsloth 的 UD-Q8_K_XL，困惑度与原版
> 小数点后四位完全相同……

技术上完全正确，数字也都对得上原文。但**没把文章讲清楚**：观众听完知道某个量化
档位的困惑度没变，却不知道这是哪个模型、发布了没有、和上一代比怎么样。

### 对照参考稿

人工撰写的稿子在 30 秒里放了**六个事实，每句一个**：

```
谁开源了什么（带完整版本号）→ 榜单得分与排名 → 激活参数 → 上下文长度
→ 速度与成本 → 能力追平旗舰 → 引导关注
```

**第一句就是事件本身。** 而生成稿的第一句是一个结论——观众还不知道在说什么。

### 改法

| 改前 | 改后 |
|---|---|
| 一条视频只讲一个点 | **覆盖文章的主干，不要只挑一个点深挖** |
| 开头 1 句给出这个点 | **第一句必须是事件本身**：谁、发布了什么、叫什么名字 |
| 围绕它讲透，不要罗列 | **每句换一个新事实**，不在同一个点上展开第二句 |
| 主标题：有冲击力 | 主标题：**就写事件本身**（「DeepSeek V4 Flash 开源」） |
| 副标题：放具体数据 | 副标题：**堆亮点与意义**（「极限量化，成本骤降，本地部署迈入新时代」） |

另外允许「更狠的是」这类短句制造节奏，但**每个短句后面必须紧跟具体数据**，
不能只有情绪——这是参考稿的实际写法。

## C. 笼统的「不要白话」模型执行不了 —— 已改

初版只说「不要用白话替代具体指标」。真机产出里仍然出现了四类问题，
都是从实际稿子里挑出来的：

| 实际出现的内容 | 问题 |
|---|---|
| 「这对做本地部署的人意味着什么？」 | **提示词里的结构提示被原样写进了稿子** |
| 「我最关注的是本地部署」「但我建议」 | 第一人称主观表达，稿子是播报不是随笔 |
| 「让企业级应用不再需要巨额硬件投入」 | 用形容词堆出来的结尾，占时长零信息 |
| 「让我们一起来看看」 | 填充语 |

改成**逐条点名**。笼统的禁令模型无法执行——它不知道自己写的算不算白话，
但它知道「不要写『我认为』」。

第一人称那条还加了替代方案：原文作者的建议要写成「原文建议」「官方推荐」，
标明出处。直接删掉会丢信息，而那些建议是有价值的。

## D. 正文被截断，局限根本没进提示词 —— 已修

### 现象

`MAX_BODY_CHARS = 3000`，而那篇文章有 4069 字。检查被切掉的最后 1069 字，
里面有：

- 采样参数：`temperature = 1.0`、`top_p = 1.0`、agentic 场景换 `0.95`、
  开 Think Max 上下文至少 384K
- **一条关键局限**：官方没给 Jinja 格式的 chat template，只提供 encoding 文件夹；
  Unsloth 补了一版并拿 4000 多轮对话对齐官方基线。
  「下别人的 GGUF 之前先确认对方有没有处理模板和 MXFP4 重打包，
  不然『能跑』和『跑对』是两回事」

**提示词要求「原文提到局限就必须说」，而最有价值的那条局限模型根本没看到。**

### 修复

文案层的上限提到 **6000 字**，摘要节点保持 3000。两者成本结构不同：

| 节点 | 跑法 | 上限的代价 |
|---|---|---|
| 摘要 | **每条都跑**，一期几十条 | 上限 × 条目数，直接乘进账单 |
| 文案 | **单篇按需**跑 | 只影响这一次调用 |

复验后短视频稿里出现了「Think Max 需 384K 上下文」——正是原先被切掉的内容。

## E. 摘要选错了指标 —— 已修

### 对照

| | 同一个位置写的是 |
|---|---|
| 本系统 | 「原生 8-bit 精度模型文件 167GB」 |
| 人工撰写的参考摘要 | 「**激活参数 13B**」 |

「1~2 句」是硬约束，装不下所有数字，所以**取舍规则必须写进提示词**。
不写的话模型按原文出现顺序取，而技术文章的开头往往是文件体积、依赖版本这类
次要细节。

### 修复

提示词里加了两条：

1. **信息要完整**：原文讲了几件事就都要覆盖到。既讲模型发布又讲第三方量化方案的
   文章，两件事各占一句，不要只写前一半
2. **挑最有价值的指标，不是最先出现的指标**，并给出优先级：
   榜单排名与得分 > 架构关键参数（总参/激活参/上下文长度）> 能力对比结论 >
   次要细节（文件体积、依赖版本、硬件型号）

## F. 参考稿里有原文没有的事实 —— 说明，不修

参考稿提到「Artificial Analysis 智能指数上得分 50」「位列开源模型前三」
「激活参数只有 13B」「支持百万 Token 的超长上下文」。

在落盘正文里逐个检索：

| 事实 | 原文里有吗 |
|---|---|
| `Artificial Analysis` | ✅ 有（但没有得分数值） |
| `智能指数` | ✅ 有 |
| `斩杀线` | ✅ 有 |
| 得分 50 / 前三 | ❌ **没有** |
| 激活参数 / 13B | ❌ **没有** |
| 百万 Token / 上下文长度 | ❌ **没有** |

这些是撰稿人从别处知道的。而提示词里有一条硬约束：

> 不确定的技术细节**宁可不写**，不要用「据说」「可能」掩盖

所以系统不会写出这几个数字——**这是正确行为**，不是缺陷。同一篇文章的
`meta.json` 就是唯一输入，编造一个「得分 50」比漏掉它危险得多。

要让这类跨源事实进到文案里，需要的是**采集侧补齐**——同一事件聚合多家来源，
把各家报道的正文都喂进去（`Cluster` 已经是这个结构，摘要节点也已经在用
「另有 N 家媒体报道同一事件」）。而不是放松提示词的约束：编造一个「得分 50」
比漏掉它危险得多。

> 多项基准超越 V4-Pro 预览版。模型仅 304B，原生 8-bit 精度，文件 167GB。

零编造。

**长文案未复跑**：按用户要求「这个功能比较贵不要频繁测试」。它继承了同一套
`PROFESSIONALISM` 与 `prompt_char_budget`，目标字数因此提高 50%。

## G. 长文案分节重复：只给上一节结尾是不够的 —— 已修

### 现象

按用户要求跑了两篇长文案：

| 文章 | 模式 | 结果 |
|---|---|---|
| CES 2026 见闻（17714 字） | 专题 | 4078 字 / 628 秒，7 节 |
| MiniMax H3（3151 字） | 访谈 | 3639 字 / 539 秒，30 轮（主持人 15 / 嘉宾 15） |

CES 那篇的第 7 节「其他创新硬件与生态」**把第 6 节几乎逐个重讲了一遍**：

```
第6节 879 字 / 第7节 238 字
两节都出现的实体：MemoMind、StarV、Leion Hey2、VOCCI RING、MLVision、
                  极米、星纪魅族、亮亮视野、Gyges  ← 9 个全部重复
```

第 7 节 238 字里没有一个新信息点。访谈那篇也有轻度重复：
「广义参考编辑完全由真实自然数据构成」在第 2 节和第 4 节各出现一次，
「100K Token 推理压缩成 4K」在第 3 节和第 4 节各出现一次。

### 根因

`previous_tail = turns[-1].text[-120:]` —— 每节只看得见**上一节最后 120 字**。

写第 7 节时模型不知道前面六节各自覆盖了什么，于是把「其他创新硬件」理解成
「再说一遍我知道的硬件」。这个节名本身也有问题：**「其他」类的节没有边界**，
写的时候只能去重复前面的内容。

### 修复（两处，都不增加调用次数）

**① 每节的提示词里放完整提纲，标出边界：**

```
全文提纲（只写标着「← 现在写这节」的那一节）：
1. CES 2026 概览（已讲过）
2. AI 陪伴硬件（已讲过）
3. 智能家居与个护美妆　← 现在写这节
4. 运动健康与宠物科技（留给后面）
...

边界要求（重要）：
- 标着「已讲过」的内容不要再讲，一个产品名、一个数字都不要重复
- 标着「留给后面」的内容不要提前讲
- 本节的料不够写满时，去原文里找本节主题下更细的数据，
  不要去写别节的内容凑长度
```

**② 提纲阶段就禁止边界模糊的节：**

- **各节内容必须互斥**，同一个产品/技术/数据只能归给一节
- **不要用「其他」「其余」「补充」命名任何一节**
- 局限那条从「必须有一节讲局限」放宽为「局限、代价、前提条件**或未解决的问题**」，
  并补充「原文没明说时讲共同短板，但只能基于原文事实」——
  CES 那篇原本压根没规划局限节，因为展会见闻类文章确实没有现成的局限段落

### 复验（同一篇 CES，9 次调用）

| | 改前 | 改后 |
|---|---|---|
| 长度 | 4078 字 / 628 秒（10.5 分钟） | **5524 字 / 902 秒（15 分钟，正好压在上限）** |
| 节数 | 7 | 8（**含「局限、代价与未解问题」**） |
| 最严重的跨节重复 | 第 6↔7 节 **9 个实体，第 7 节零新信息** | 第 2↔8 节 6 个实体，**且是局限节在点评前面的产品** |

改后剩下的「重复」是**预期行为**：局限节必须点名它在批评什么。实际内容是

> BOOBOO、NICOBO 这类情感陪伴机器人，形态讨巧，但能否让用户长期留存，目前没有
> 数据支撑……AIPi 以 22 美元起价，几乎是硬件界的价格屠夫，但如此低价要么牺牲性能，
> 要么毛利微薄……Rokid Style 做到 38.5 克，确实轻，但为了轻，功能上必然有所取舍

——引用的数字（22 美元、38.5 克、7 小时、78 克、BES2800）全部来自原文。

### 遗留：局限节的判断是推测出来的

原文是展会见闻，**没有任何一段讲局限**。所以「必须有一节讲局限」逼着模型
自己推断，产出里因此出现了「能否持续迭代要打问号」「可能不如云端大模型」
这类带不确定语气的判断——而 `PROFESSIONALISM` 第 4 条明确禁止用「可能」掩盖。

这是一对**真实的规则冲突**，不是 bug：

| 选项 | 代价 |
|---|---|
| 保持现状 | 局限节含推测，语气偏软，但内容基于原文数据且有价值 |
| 改成「原文没讲局限就不生成这一节」 | 见闻/发布稿类文章的长文案会变成纯罗列，没有观点 |
| 单独给局限节放开推测，但要求标注「这是推断」 | 稿子里出现「以下是我的推测」，口播出来很怪 |

**用户决定（2026-09-04）：以原文为主，保持现状**——局限节可以含推测，
但推测必须**建立在原文给出的数据上**（38.5 克、7 小时、22 美元这些都来自原文），
不引入原文没有的事实。提示词里那句「只能基于原文里的事实，不要凭空推测」
即是这条边界，保留不改。
