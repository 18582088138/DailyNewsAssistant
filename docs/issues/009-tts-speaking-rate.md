# 009 — TTS 实测语速与文案时长估算差 63%

> 状态：⚠️ **已量出，本阶段不改**。等发布加速倍率定下来再一起校准。
> 发现于 P4.5 首次真机合成，2026-09-04。

---

## 现象

口播稿的台账记录写着「约 93.9 秒」，合成出来的音频是 **153.3 秒**。

```bash
$PY -m frontends.cli.main produce decef4a4 --kind narration_audio
#   ● 口播音频：827 字，约 153 秒

$PY -c "from dna.tts import wav_seconds; from pathlib import Path; \
        print(wav_seconds(Path('<产物目录>/narration.zh.wav').read_bytes()))"
# 153.3
```

| | 值 |
|---|---|
| 稿子估算 | 93.9 秒 |
| 实际音频 | 153.3 秒 |
| 差 | **+63%** |
| 朗读字数 | 827 |
| **Qwen3-TTS 实测语速** | **5.4 字/秒** |

对照 issue 008 里量过的另外两个语速：

| 来源 | 语速 |
|---|---|
| 用户手写参考稿（人读） | 7.2 字符/秒 |
| `duration.py` 的纯中文常数 | 4.5 字/秒 |
| `duration.py` 的混排预算（4.5 × 1.5） | 6.75 字符/秒 |
| **Qwen3-TTS 合成** | **5.4 字/秒** |

---

## 为什么本阶段不改

三条：

**1. 加速倍率还没定。**用户明确说过发布的视频会做加速播放，
但倍率是人定的、每期可能不同。153 秒按 1.5× 播出来是 102 秒，
和 93.9 秒的目标基本对上；按 1.0× 就是超一倍。
在倍率确定之前动语速常数，只是把一个偏差换成另一个偏差。

**2. 改语速会连带改文案长度。**`target_chars` 是 `estimate_seconds` 的严格反函数，
改常数等于改所有稿子的目标字数——而这套字数刚在 issue 008 里按用户手写的参考稿
校准过一轮，人工审阅也过了。为一个还没定的倍率去推翻一轮已验收的校准，
顺序是反的。

**顺带的一个后果：界面上的预估等待也偏低同样的倍数。**
`audio_estimate_seconds` 是「稿子估算时长 × RTF」，稿子那一项低 63%，
预估就跟着低——口播那篇显示 235 秒，实际跑了约 380 秒。
这不单独修：修它等于在错误的基数上再乘一个修正系数，把一个可解释的偏差
变成两个纠缠在一起的魔数。基数对了，预估自然就对了。

**3. 现在两个数都在台账里，看得见。**稿子那行记的是估算 93.9 秒，
音频那行记的是**真实时长** 153.3 秒。偏差不会被藏起来，
攒够几篇就能看出它是稳定的 1.63 倍还是随稿子波动。

## 下次动它的时候要先回答

- 发布加速倍率定成多少？固定还是每期调？
- 5.4 字/秒 是不是稳定值？换音色（serena → uncle_fu）会不会变？
  换语言（中英混排比例不同）会不会变？
- 目标应该对齐**合成时长**还是**加速后的成片时长**？
  后者才是观众实际听到的，但它多一个人为变量。

至少攒 5 篇不同长度、不同中英比例的稿子的实测值再动。
一篇的数据不足以区分「常数错了」和「这一篇恰好偏慢」。
